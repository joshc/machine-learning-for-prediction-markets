    Editorial and implementation contract¶

    This file defines the shared conventions for this original book and its companion. It is contributor documentation, not a chapter in the reading sequence.

    Scope and voice¶

    Write for a Python-capable reader who knows basic probability but not quantitative finance. Explain the economic or statistical question before introducing notation or an algorithm. Teach from first principles. The complete book targets 60,000-90,000 words; substantive chapters should generally contain 2,000-2,800 useful words rather than compressed outlines.

    Do not consult, reproduce, paraphrase chapter-by-chapter, or reuse code from the linked Packt textbook. Use primary research and original worked examples. Do not imply that prediction markets themselves lack a long research history.

    Each chapter needs a descriptive title, prerequisites, learning objectives, a motivating case, developed explanations, assumptions and failure modes, worked reasoning, a companion-example link where appropriate, exercises, and solution sketches. Put exercise solutions in the chapter for reliable local context; solutions.md will provide navigation rather than duplicate them.

    Use ordinary, direct prose, not marketing copy. Label empirical evidence, mathematical derivations, synthetic illustrations, and hypotheses accurately. Never fabricate data, measured performance, a source, or a verification claim. A negative or inconclusive experiment is a legitimate result.

    Stable shared conventions¶

    contents.json fixes chapter filenames, order, and companion script names. Do not change it from an author workstream. Use the notation in notation.md.

    Illustrative contracts pay USD 1 per unit if YES and zero if NO, unless an example explicitly introduces a different payout. Actual venues may have different collateral or exceptional settlement; identify those separately.

    Use a canonical accounting example across the book: buy 10 YES units at USD 0.40, with a hypothetical flat USD 0.01 fee per unit, and hold to binary settlement. Initial cost is USD 4.10, profit is USD 5.90 on YES or minus USD 4.10 on NO. At a model probability of 0.55, modeled expected net profit is USD 1.40. This is a cost illustration, not an actual venue fee or empirical edge. A sale at USD 0.46 with a further USD 0.01-per-unit exit fee produces USD 0.40 realized profit.

    Report Brier score for a binary outcome as the mean of one squared YES-probability error per event, not twice that value. Use natural logarithms for log loss. State exact zero/one handling rather than silently clipping probabilities.

    Keep event time, source publication time, local observation time, decision time, fill time, label availability time, and settlement time distinct. Use timezone-aware UTC timestamps. Repeated snapshots or contracts sharing a realized event are not independent labels. A time gap alone does not cure an event-group leak.

    Use executable asks for buying and bids for selling; a midpoint is a forecasting benchmark, not a fill. Treat fees, collateral, depth, partial fills, latency, cancellation, adverse selection, and settlement consistently. Never infer resting-order fills from quote touches alone. Do not assume all complementary questions share the same resolution rules.

    Sources and claims¶

    The shared book\research\sources.json (from the trading repository root) is a JSON array of source objects. Each object has id, title, authors (array), year, kind, status, url, doi (nullable), accessed, verification, supports (array), and limitations (array). Additional useful fields such as locator are permitted. Verification must honestly distinguish full-text inspection, abstract/metadata inspection, and official documentation.

    From chapter files, use bibliography links such as [WZ2006](../references.md#wz2006) for source-backed statements. Bibliographic sections use ## WZ2006 so the lowercase key is a stable anchor. Never add a citation key that does not exist in the ledger without coordinating the addition.

    Authors own their chapter files and one CSV fragment at book\research\claim-fragments\<group>.csv; do not edit the shared ledger, aggregate claim map, reference list, contents, notation, or another author's files. CSV columns are claim_id,chapter,claim,source_ids,locator,evidence_type,limitations. Separate multiple source keys with semicolons. Map material nontrivial sourced claims to a section/table/theorem/page when supported. A derived classroom identity does not need to masquerade as an empirical citation.

    Primary research is not automatically true or transferable to prediction markets. Label stock-market microstructure results as analogies with assumptions. Working papers are not peer-reviewed journal articles. "Source exists" is not the same as "source supports this sentence." If only an abstract was inspected, keep the claim within that abstract or flag the full-text requirement.

    Runnable companion boundary¶

    Examples import shared implementations from prediction_market_lab; avoid duplicating accounting or statistical helpers in chapter snippets. Their project root and virtual environment live in book\companion. Starting from the trading repository root, canonical commands use:

    Set-Location book\companion
.\.venv\Scripts\python.exe examples\payoffs.py

    Follow the companion README for installation; create .venv and run package installation from book\companion, not the Git root. All default examples are offline, deterministic, labeled teaching demonstrations. Do not invent API methods, flags, filenames, result values, or measured accuracy. Read the completed example before documenting its actual output.

    The educational companion has no funded-order submission, signing, deposit, or live-mode flag. Optional external acquisition is explicit and read-only. This boundary does not describe unrelated trading-system code at the repository root. The final live-trade chapter is a manual checklist, not an automation recipe.

    Chapter authors may explain a future experiment, but must distinguish a proposed procedure from an implemented capability. A historical price series or synthetic book does not support a claim of historically executable profit.

    Review standard¶

    Technical review covers calculations, claims, inference, data provenance, and executable behavior. A separate editor reads all 30 complete chapters in order, including transitions and supporting reference material. Reports must identify actual coverage, material findings, fixes, and limitations; no unsupported claim of academic peer review or certified profitability.

    Use GitHub Markdown math ($...$ and $$...$$). Use URI separators in Markdown links and Windows backslashes in shell/file-access paths. Keep new source files ASCII unless a particular existing format requires otherwise.
