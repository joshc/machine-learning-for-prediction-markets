    28. Scan for inconsistent contract prices¶

    Prerequisites¶

    You should be comfortable with the cross-market and no-arbitrage-constraint reasoning of Chapter 20, the rules-and-settlement discussion of Chapter 6, and the paper-broker accounting from Chapter 24. You need to know what sweep_cost, FeeSchedule, and executable depth mean from Chapter 5's market-microstructure material, and you should already understand why a paper fill is not a live fill.

    Learning objectives¶

    By the end of this chapter you should be able to run the consistency-scanning quickstart, explain exactly what manual verification step makes a basket a candidate rather than an automatic trade, distinguish a depth failure from a compatibility failure, and compute by hand the loss that results when only one leg of a multi-leg basket fills before the position is settled against you. You should also be able to state precisely why this scan cannot be, and is not, driven by matching contract titles or natural-language similarity.

    28.1 A concrete goal: scanning one exhaustive, mutually exclusive partition¶

    The idea behind this quickstart is old and simple: if a set of contracts covers every possible outcome of one event, exactly once each, then buying one YES unit in every contract in the set guarantees exactly one of them pays out, so the position's minimum possible payout is fixed and known in advance. If the total cost of buying all legs is less than that guaranteed minimum payout, the position has a positive payoff floor before any model or forecast is involved at all. This is a classical no-arbitrage-style construction, not a forecasting technique, and its entire value depends on the partition genuinely being complete, mutually exclusive, and governed by one resolution process.

    Run the script from the companion project root (book\companion):

    Command working directory: run this chapter's Python commands from book\companion. From the trading repository root, run Set-Location book\companion once first. The .venv belongs to that companion project; see companion setup.

    .\.venv\Scripts\python.exe examples\quickstart_consistency.py

    Open examples/quickstart_consistency.py while reading. It defines three invented contracts over the states "low", "middle", and "high", each paying USD 1 exactly when its own state is realized and zero otherwise, an explicit, hand-constructed complete partition. Each leg's order book quotes bid 0.25 and ask 0.30, with only four units of executable ask depth per leg (ask_size=4).

    28.2 Reading the actual output¶

    The observed run includes the following excerpt (some wrapper and explanatory fields are omitted):

    {
  "result": {
    "verified_partition_candidate": {
      "status": "PAPER_CANDIDATE_ONLY",
      "quantity_each": 4, "total_cost": "3.72", "required_cash": "3.72",
      "minimum_payout": "4.00", "minimum_net_profit": "0.28",
      "reason": "conditional on complete verified payout states and all legs filling"
    },
    "depth_failure": {
      "status": "NO_TRADE", "quantity_each": 0,
      "total_cost": null, "required_cash": null, "minimum_payout": null, "minimum_net_profit": null,
      "reason": "insufficient executable depth for the requested full size"
    },
    "only_first_leg_fills_then_loses_profit": "-1.24",
    "required_manual_checks": [
      "same event and resolution source", "complete exceptional payout state space",
      "fresh executable depth", "fees", "funded capital", "non-atomic leg failure"
    ]
  }
}

    At quantity 4, each of the three legs costs \(4 \times (0.30 + 0.01) = 1.24\) to buy at the ask with the fixture's flat USD 0.01 fee, for a total cost across all three legs of \(3 \times 1.24 = 3.72\), matching total_cost. Because exactly one state resolves YES, the guaranteed minimum payout is \(4 \times \text{USD }1.00 = 4.00\) regardless of which of the three states occurs, since whichever leg wins pays exactly \(4 \times 1\) and the other two pay zero. The minimum net profit is \(4.00 - 3.72 = 0.28\), conditional on every leg actually filling at the quoted price and the partition genuinely being complete. scan_basket reports this as PAPER_CANDIDATE_ONLY, not as an executed trade or a certain profit; the leg_risk field attached to every BasketResult, "non-atomic legs can fail; quoted basket is not guaranteed execution", is repeated for exactly this reason.

    required_cash is separate from total_cost. They equal USD 3.72 here because each leg has one cent-aligned price and a cent-aligned flat fee, so fragmented reservation rounding adds nothing. The field is the larger of modeled full-fill cost and summed reservations under the teaching broker's conservative rules, not an implementation of real venue collateral requirements. Differences can arise from deeper executable limits and per-fill rounding even when a snapshot has only one price level. Check both cost and required cash before treating the requested size as funded.

    At quantity 5, the same three legs each have only 4 units of executable ask depth, so scan_basket correctly reports NO_TRADE with reason "insufficient executable depth for the requested full size", and every numeric field, including required_cash, is null rather than a fabricated partial-fill estimate. The script does not attempt to silently fill 4 of the requested 5 units and report a scaled-down profit; an unmet request is reported as a clean rejection with an explicit reason, which is the same fail-closed discipline used throughout the companion's risk and operations modules.

    28.3 The loss when only one leg fills: only_first_leg_fills_then_loses_profit¶

    The most important number in this script is -1.24, and it is worth tracing through completely, because it is the concrete answer to the question "what happens if I attempt this basket and only some of it actually executes." The script submits and fills only the "low" leg: 4 units bought at the 0.30 ask with the same USD 0.01 fee, for a cost of \(4 \times (0.30+0.01) = 1.24\), exactly matching the single-leg cost computed above. It then settles that one contract at a payout of zero, with the settlement comment "invented middle state; other legs never filled". Because only the "low" leg was ever submitted, and its state did not occur, the broker's realized profit is \(0 - 1.24 = -1.24\).

    This is not a contrived worst case invented to scare the reader. It is the literal, arithmetic consequence of a basket strategy's central operational risk: the legs are separate contracts on separate order books, executed as separate orders, and nothing in the system guarantees they fill together, at the same moment, at the quoted prices, or at all. If a trader submits all three legs of this basket and only one fills, perhaps because the other two books moved, emptied, or were cancelled before the trader's orders reached them, the trader is left holding a single directional bet with none of the completing legs that made the original arithmetic attractive. The 0.28 minimum profit computed in Section 28.2 was conditional on every leg filling; a partial fill removes that conditioning entirely and can leave a straightforward loss, exactly the -1.24 shown here.

    28.4 What makes a partition candidate, and why that check cannot be automatic¶

    scan_basket accepts a compatibility_verified flag, and in this script it is passed as the literal True, supplied by the person writing the script, not computed by any code in the package. Read _compatible in prediction_market_lab.constraints: it checks that compatibility_verified is exactly True, and that all legs share the same event_id, rules_id, currency, and set of declared payout states. None of this is derived from comparing contract titles, descriptions, or any natural-language similarity between the three contracts' names. Two contracts whose short titles look related, for example two headlines both mentioning the same underlying quantity, are not thereby verified to share one resolution process, one exceptional-settlement rule, or one complete state space; that verification is a human responsibility, informed by actually reading both contracts' rules, not a property any string-matching or embedding-similarity check could establish.

    The required_manual_checks list printed by the script names exactly what that human responsibility covers, and each item deserves its own explanation rather than a bare repetition of the label:

    • Same event and resolution source. Two contracts can describe superficially similar questions while resolving from different official sources, different observation windows, or different underlying definitions. A partition is only exhaustive and mutually exclusive with respect to one shared resolution process; if the three legs here actually resolved from different sources, "exactly one of them pays" is no longer guaranteed.
    • Complete exceptional payout state space. This script's legs pay one dollar or zero. The inspected Polymarket resolution page documents an exceptional 50/50 payout; it does not establish a generic void or refund convention. POLYMARKET_RESOLUTION Check any tie, cancellation, refund, or other exceptional rule in the specific contracts. A genuinely possible omitted state invalidates a claimed complete payout floor, while a 0.50/0.50 pair can still retain a constant combined payout.
    • Fresh executable depth. The quoted ask and its size must reflect a currently valid, unexpired snapshot, not a stale quote from moments or minutes earlier; validate_at enforces a maximum quote age precisely because a basket built from mismatched-in-time snapshots is not describing one coherent market moment.
    • Fees. This script's flat USD 0.01 per unit is an invented teaching cost. Real fee schedules can be price- and size-dependent, as the inspected Kalshi and Polymarket documentation both describe; KALSHI_ROUNDING POLYMARKET_FEES a basket margin computed with the wrong fee model can turn an apparent profit floor into a loss floor.
    • Funded capital. scan_basket compares required_cash, the larger of the total fill cost and the summed worst-case per-leg reservation at each leg's executable limit price, against a stated capital argument, and rejects the basket outright, with reason "funded capital cannot reserve all basket orders before execution", if that larger figure would exceed it. Because reservation and fill cost can round differently per leg and per fill, required_cash is not always identical to total_cost, so a reader sizing a basket must check the reported required_cash, not just the fill-cost total, and the capital figure itself, and whether it is genuinely available and not already committed elsewhere, remains the caller's responsibility to state honestly.
    • Non-atomic leg failure. Section 28.3's -1.24 result is the concrete consequence of ignoring this check. Nothing in a typical venue guarantees that submitting three separate orders results in three simultaneous fills; a plan that only works if all legs fill together needs an explicit answer for what happens if they do not.

    28.5 A concrete illustration of why titles are not rules¶

    Suppose one rule pays YES when an index closes strictly above 100, while another pays YES at or above 100. With the same index, time, and precision, these are nested events, not complements, and they differ exactly at 100. Buying YES on the strict-above contract and NO on the at-least contract pays zero on both at that boundary. The reverse pair pays on both there. Neither basket has the ordinary exactly-one-winner property. Check the rules' inequalities and measurement precision, not just their similar titles.

    The same caution applies even more strongly across two different underlying instruments that merely sound related, two different index providers measuring a similar quantity, or two contracts on the same nominal event hosted by different venues with different resolution sources and different dispute processes. scan_basket's _compatible check only inspects event_id, rules_id, currency, and the declared set of payout-state names on BasketLeg objects that a human has already constructed; it has no access to, and makes no attempt to interpret, either contract's actual title text. This is a deliberate boundary, not a missing convenience feature. A short title is a marketing-quality summary; a rules document, read in full by a person who understands where its boundary conventions and exceptional-payout provisions live, is the only thing that can establish whether "same event, complete partition" is actually true, which is exactly why compatibility_verified must be supplied by that person and cannot be inferred by matching strings or embeddings, however similar two descriptions might look at a glance.

    28.6 Troubleshooting¶

    Setting compatibility_verified=False makes scan_basket return REJECTED with unset cost fields. Nonempty but different state-key sets across legs produce the same compatibility rejection in the scan; an individual BasketLeg cannot compare itself with legs it has not seen. Its constructor instead raises "an explicitly complete state space is required" for an empty mapping or empty state name. That structural check cannot establish real-world completeness. Stale or future books are caught by scan_basket and returned as NO_TRADE, not propagated as quote-age exceptions; malformed quantities or invalid leg construction can fail earlier.

    28.7 Exercises and solution sketches¶

    Exercise 1: recomputing the basket at a different quantity¶

    Using the same three-leg fixture, compute the total cost, minimum payout, and minimum net profit at quantity 3 instead of 4, still within the 4-unit depth limit.

    Solution sketch. Per-leg cost is \(3\times(0.30+0.01)=0.93\); across three legs, total cost is \(3\times0.93=2.79\). Minimum payout is \(3\times1.00=3.00\). Minimum net profit is \(3.00-2.79=0.21\), still conditional on all three legs filling and the partition remaining verified and complete.

    Exercise 2: why a two-state partition is not automatically the same as a two-outcome market¶

    A market interface might display "low" and "not low" as if they were two contracts covering a full binary partition. Explain what would need to be true for this displayed pair to satisfy the same compatibility requirements as this chapter's three-state example.

    Solution sketch. "Not low" would need to be an actual tradable contract, sharing the same event, resolution source, currency, and payout convention as "low," and its payout would need to be exactly the complement of "low" in every possible resolved state, including any exceptional or void outcome. A user-interface grouping of two labels is not itself evidence of this; the same manual checks from Section 28.4, particularly complete exceptional-state coverage, apply identically to a two-leg partition as to a three-leg one.

    Exercise 3: pricing the effect of a fee change¶

    Suppose the flat fee in this fixture were raised from USD 0.01 to USD 0.03 per unit, with the ask still at 0.30 and quantity still 4. Recompute the total cost and minimum net profit, and state whether the basket would still be reported as a candidate.

    Solution sketch. Per-leg cost becomes \(4\times(0.30+0.03)=1.32\); total cost across three legs is \(3.96\). Minimum payout remains \(4.00\), so minimum net profit falls to \(0.04\). The basket would still clear scan_basket's strictly-positive-profit check and be reported as PAPER_CANDIDATE_ONLY, but with a much thinner margin, illustrating how sensitive a small guaranteed floor can be to an unverified or outdated fee assumption.

    Exercise 4: a different single filled leg¶

    Suppose instead the "middle" leg is the one that fills, at the same 4-unit quantity and price, and the eventual state is "high". Compute the realized loss using the same method as Section 28.3.

    Solution sketch. Cost is identical, \(4\times(0.30+0.01)=1.24\); the payout for holding only the "middle" leg when "high" occurs is zero, since "middle" did not resolve. Realized profit is \(0-1.24=-1.24\), the same magnitude as the chapter's worked example, because the arithmetic depends only on which single leg filled and whether it happened to be the one that ultimately resolved YES, not on which specific label was involved.

    Exercise 5: a boundary-convention mismatch¶

    Two contracts are titled "closes above 100" and "closes at or below 100," and a reader assumes without reading either rules document that they form a complete two-state partition. State one concrete boundary scenario under which buying one of each could leave the trader with neither leg paying out, and explain what document would have revealed this risk in advance.

    Solution sketch. If the first contract's rules define "above" as strictly greater than 100, and the second contract's rules were independently written by a different desk to mean "at or below 99," a closing value of exactly 100 would fail both contracts' stated conditions, leaving no leg paying out despite the titles suggesting full coverage. Only each contract's own rules document, read directly rather than inferred from its title, would reveal this specific boundary gap; this is precisely why compatibility_verified in scan_basket must be a human's affirmative, informed judgment rather than a string comparison between two headlines.

    Exercise 6: why required_cash can exceed total_cost¶

    The companion's own regression tests verify a two-leg basket at quantity 3, with a per-unit fee of USD 0.001 and both legs' ask quoted at 0.3333: total_cost is 2.02 but required_cash is the larger 2.10, so a capital of 2.02 is rejected while 2.10 is accepted. Reconstruct both figures by hand and explain why they differ.

    Solution sketch. Use Chapter 17's cent-ceiling notation \(\lceil x\rceil_{0.01}=0.01\lceil x/0.01\rceil\), not a whole-dollar ceiling. Each leg's aggregate notional \(3(0.3333)=0.9999\) rounds half-up to USD 1.00; its fee is \(\lceil0.003\rceil_{0.01}=0.01\), giving USD 1.01 per leg and USD 2.02 total. Each reserved unit instead allows \(\lceil0.3333\rceil_{0.01}=0.34\) plus \(\lceil0.001\rceil_{0.01}=0.01\): USD 0.35 per unit, USD 1.05 per leg, USD 2.10 total. This is a conservative cash bound, not a change to the four-decimal quoted price grid. required_cash is the larger of summed reservations and modeled fill cost.
