    13. Forecasts that evolve with time¶

    Prerequisites¶

    Read Chapters 11 and 12 first; this chapter reuses the same fixture, the same three-feature EventRow representation, and the point-in-time discipline established there. You should be comfortable with conditional probability, Bayes' rule, and simple weighted averages. The notation registry distinguishes event time, decision time, and label-availability time; that distinction is the organizing idea of this chapter.

    Learning objectives¶

    By the end of this chapter you should be able to: derive a sequential Bayesian update and apply it to a chain of successive evidence; derive a scalar, variance-weighted combination of a prior estimate and a new observation in the style of a linear filter, and state why bounded [0,1] probabilities should not be assumed Gaussian without justification; explain when a survival/hazard framing is actually appropriate for a prediction-market question, and why modeling when something resolves is a different exercise from modeling the probability of YES itself; and read the companion's two-snapshot example correctly, without treating repeated observations of one event as independent evaluation trials.

    13.1 A forecast is not fixed the moment it is made¶

    Every model built in Chapters 11 and 12 produces a single forecast from a single feature vector at a single decision time. But an actual event contract is typically observed repeatedly before it resolves: new information arrives, scheduled releases occur, and the horizon to resolution shrinks. A forecasting system that only knows how to answer "what is \(\hat p\) given \(x\) right now" still needs a disciplined way to handle the fact that \(x\), and therefore \(\hat p\), changes as the event approaches.

    The companion fixture makes this concrete without needing a real data feed. Each synthetic event in generate_recurring is observed at two decision times, 12 hours and 3 hours before resolution, with a fresh, independently noised signal feature at each decision time. This is not a second independent draw of the outcome — it is the same underlying event, observed twice, at two different amounts of remaining uncertainty. This chapter is about the machinery for reasoning across that kind of evolving observation sequence, and about the specific labeled traps in doing so carelessly.

    13.2 Sequential Bayesian updating from first principles¶

    Chapter 11 already used single-step Bayes' rule; the sequential case simply chains it. Given a prior probability \(p_0\) and a sequence of evidence items \(e_1, e_2, \ldots\), each conditionally informative about the same underlying event, Bayes' rule after the first item is

    \[ p_1 = \frac{p_0 \cdot P(e_1\mid Y=1)}{p_0\cdot P(e_1\mid Y=1) + (1-p_0)\cdot P(e_1\mid Y=0)}, \]

    and the posterior \(p_1\) becomes the prior for the next update using \(e_2\), and so on. This is exactly the book's bayes_update function applied repeatedly, and it is worth checking on a small chain to see the mechanics rather than trust the formula from memory.

    Start at \(p_0=0.30\). Suppose a first bulletin has likelihood ratio \(P(e_1\mid Y{=}1){=}0.70\) against \(P(e_1\mid Y{=}0){=}0.40\): the update gives \(p_1 = 0.30(0.70)/[0.30(0.70)+0.70(0.40)] = 0.428571\). A second bulletin with \(P(e_2\mid Y{=}1){=}0.65\) against \(P(e_2\mid Y{=}0){=}0.45\) updates \(p_1\) to \(p_2 = 0.428571(0.65)/[0.428571(0.65)+0.571429(0.45)] = 0.520000\) (both values checked with a script). Two pieces of moderately informative evidence moved the belief from 0.30 to 0.52 — noticeably, but not dramatically, which is the correct behavior of Bayes' rule when neither piece of evidence is overwhelming on its own.

    This chain-of-updates view has an important, easy-to-miss requirement: each \(e_i\)'s likelihoods must be genuinely conditionally independent given \(Y\), or specified jointly if they are not. Two bulletins drawn from the same underlying report, restated in different words, are not two independent pieces of evidence, and feeding both into a naive sequential update as if they were double-counts whatever the shared report actually established. The companion's two-snapshot fixture sidesteps this by using latest_per_event to collapse each event to one row before scoring (Chapter 11); this chapter's sequential-update machinery is a separate tool for cases where you genuinely intend to combine successive, distinct evidence about one still-unresolved event, not a license to treat every repeated observation as new information.

    13.3 A scalar state-space idea: combining a prior estimate with a new observation¶

    A related but distinct problem: suppose you already have a running numerical estimate \(m_0\) of some quantity, with an associated uncertainty (variance) \(v_0\), and a new noisy observation \(z\) arrives with its own variance \(r\). How should you combine them? KALMAN1960 is the foundational reference for the general linear-filtering answer to this question in a state-space setting; the scalar case, which this book derives independently rather than reproducing from the unread full text, is simple enough to check by hand.

    If \(m_0\) and \(z\) are unbiased estimates of the same quantity with independent errors of positive variances \(v_0\) and \(r\), the variance of \((1-K)m_0+Kz\) is \((1-K)^2v_0+K^2r\). Differentiating gives \(-2(1-K)v_0+2Kr=0\), and the second derivative is \(2(v_0+r)>0\). Thus the minimum-variance linear combination is

    \[ K = \frac{v_0}{v_0+r}, \qquad m_1 = m_0 + K\,(z-m_0), \qquad v_1 = (1-K)\,v_0. \]

    \(K\) (the "gain") is between 0 and 1: as \(r\to0\) (the new observation is nearly noise-free), \(K\to1\) and \(m_1\to z\); as \(r\to\infty\) (the new observation is nearly useless), \(K\to0\) and \(m_1\to m_0\). A worked instance: \(m_0=0.55\), \(v_0=0.04\), \(z=0.62\), \(r=0.01\). Then \(K=0.04/0.05=0.8\), \(m_1=0.55+0.8(0.07)=0.606\), and the updated variance \(v_1=(1-0.8)(0.04)=0.008\) (checked with a script) — smaller than either input variance, reflecting that combining two independent estimates is never worse, in expected squared error, than using either alone.

    This linear-estimation derivation requires finite variances, unbiasedness, and the stated error covariance; it does not require Gaussian errors or an unbounded target. Moreover, when both input estimates lie in \([0,1]\), the convex average with \(0\leq K\leq1\) stays there. What needs extra assumptions is interpreting these formulas as an exact Bayesian posterior mean and variance, or repeatedly propagating a Gaussian state distribution. A Gaussian probability-state model can assign mass outside \([0,1]\), and a noisy observation of an underlying signal need not itself be a valid probability. One can model a transformed state such as log-odds, but then the observation model and transformation of uncertainty must also be specified. Independent unbiased probability estimates with known variances are not automatically available just because two models report numbers.

    13.4 Scheduled releases and repeated snapshots, revisited¶

    Run the companion script:

    Command working directory: run this chapter's Python commands from book\companion. From the trading repository root, run Set-Location book\companion once first. The .venv belongs to that companion project; see companion setup.

    .\.venv\Scripts\python.exe examples\forecast_models.py

    Its output includes a block labeled same_event_updates_not_independent_trials: for one held-out event, the same fitted (frozen) logistic model is applied to that event's two decision-time snapshots, 12 hours and 3 hours before resolution. On the run recorded here, the reported probabilities are 0.258916 at the 12-hour snapshot and 0.258227 at the 3-hour snapshot — barely different, even though the actual signal feature differs between the two snapshots (it is drawn with less noise at the closer horizon in the fixture's construction). The script's own label for this limitation is exact: the model is frozen at its original training-period fit and merely re-scored at two snapshots, so its calibration at the earlier, noisier horizon is unvalidated by anything in this exercise.

    Be precise about what this demonstration is and is not. It is not an application of Section 13.2's sequential Bayesian updating (nothing here chains a posterior from the 12-hour snapshot into a prior for the 3-hour snapshot), and it is not a fitted sequence model of any kind — not a recurrent network, not a state-space filter, not a model whose parameters were estimated from how an event's own history evolves over time. It is one ordinary, time-independent classifier from Chapter 11, fit once on cross-sectional training rows, applied twice to two snapshots of one event that happen to arrive at different horizons. Sections 13.2 and 13.3 describe machinery that could, in principle, treat successive observations of one event as a genuine updating chain; the companion does not currently implement either one, and this section's two-number result should not be mistaken for evidence that it does.

    This is deliberately shown, not hidden, because it illustrates a genuine limitation rather than a success. A logistic model fit once on training data does not automatically know how to weight information differently as an event's horizon shrinks; if the relationship between signal and the outcome genuinely changes with horizon (which the fixture's construction, using less noise at 3 hours, suggests it should), a single frozen model applied at both horizons is not exploiting that difference, and a more horizon-aware model — for instance, one that includes horizon as an interacting feature, or that is fit and calibrated separately per horizon bucket — would need its own dedicated validation before being trusted. Nothing in this book's companion currently implements that more elaborate design; the honest lesson from this section is naming the gap, not claiming to have closed it.

    The evaluation implication is the one already established in Chapter 11 and repeated here because it is easy to forget under time pressure: the two snapshots of one event are not two independent test cases. Reporting a score across "all snapshot rows" rather than "one row per event" would silently inflate the apparent sample size and could let an event whose two snapshots happen to agree with the label count twice toward an apparently strong score. latest_per_event exists specifically to prevent this, and any custom evaluation code you write for a sequential or state-updating model needs the same discipline.

    13.5 Survival and hazard models, and where they actually apply¶

    A different, and frequently confused, question is not "what is the probability the underlying proposition is YES" but "how long until this contract resolves." These are genuinely different targets, and conflating them is a specific, named failure mode this chapter asks you to avoid.

    Survival analysis models the distribution of a time-to-event, \(T\), often through the hazard function

    \[ h(t) = \lim_{dt\to 0}\frac{P(t\le T< t+dt \mid T\ge t)}{dt}, \]

    the instantaneous rate of the event occurring at time \(t\), given it has not yet occurred. COX1972 proposes the widely used proportional-hazards form \(h(t\mid x) = h_0(t)\exp(\beta\cdot x)\), where covariates multiply an unspecified baseline hazard \(h_0(t)\) rather than requiring you to specify its exact shape. This is a genuinely useful model when the question you actually care about is a time, such as "how many days until this contract's resolution is published" or "how long until a recurring threshold is first crossed," and when a proportional-hazards assumption (that covariate effects scale the hazard multiplicatively at every time, rather than changing its shape) is independently justified for your specific contract, not merely borrowed because the model has a well-known name.

    It is not automatically the right model for the ordinary binary YES/NO question this book has otherwise focused on, and applying it there without justification confuses two different things that this chapter's title deliberately keeps separate: an event's occurrence (did the underlying proposition come true) and its settlement (when and how the contractual payout is actually determined and released). A contract can be economically decided well before its formal settlement completes, or its settlement can be delayed by review or dispute processes unrelated to the underlying proposition's truth. If your genuine research question concerns settlement timing or delay risk — a legitimate and often underexplored question — a hazard model of the time to settlement, built from contract-level data about actual settlement delays, is the right tool; it says nothing by itself about the probability that the underlying proposition resolves YES, which remains a separate binary-outcome forecasting problem of the kind built in Chapters 11 and 12.

    A small illustration uses discrete conditional occurrence probabilities, not the continuous-time rate defined above: let \(h_1=0.10\), \(h_2=0.15\), \(h_3=0.20\), and \(h_4=0.25\) be the probabilities of occurrence during each week conditional on survival to its start. The week-by-week occurrence probabilities are \(0.100000\), \(0.135000\), \(0.153000\), and \(0.153000\), leaving survival probability \(0.459000\). They sum to one. If a contract actually asks whether this same first-occurrence event happens by week four, its YES probability is \(1-0.459=0.541\): a time-to-occurrence model can answer a binary deadline question. A model of administrative settlement delay cannot be substituted for that occurrence model.

    13.6 A brief note on detecting regime changes¶

    A related, forward-looking idea worth naming without overclaiming: ADAMS2007 derives an online algorithm for maintaining a posterior distribution over the "current run length" since the last change in an underlying data-generating process, under a changepoint model where the parameters before and after a change are assumed independent. This is conceptually attractive for a forecasting system that suspects the relationship between features and outcomes shifts over time (a market family's dynamics changing after a rule update, for instance), but the abstract's own assumption — independent before/after parameters — is a modeling choice that needs justification, and a detected changepoint is a statistical signal, not proof of a causal regime shift or evidence that a new trading opportunity has appeared. This book's companion does not implement online changepoint detection; it is mentioned here as a named, citable direction for a reader who wants to extend the sequential-updating ideas of Section 13.2 into a setting where the underlying relationship is not assumed constant, with the same caution applied to any other model in this part of the book: a fancier update rule does not, by itself, verify that it is tracking something real.

    13.7 A real-data illustration of current-vintage versus point-in-time tension¶

    The book's separate NOAA Mauna Loa monthly carbon-dioxide study, described in full in experiments/README.md, is a completed, frozen, real-data illustration of a theme this chapter has treated abstractly: a series that evolves over time is not automatically a point-in-time series, and a strong recurring pattern is not automatically a prediction-market result. The design was predeclared before acquisition or scoring, and its recorded results are hash-verified rather than adjusted after the fact.

    The predeclared question is whether a calendar-month-specific ("seasonal") event rate improves on an expanding overall rate for recorded monthly increases. Both use the Beta smoothing introduced in Chapter 11, Section 11.5: add one success and one failure to the admitted counts. The overall model pools all admitted labels; the seasonal model uses only the target calendar month's admitted labels. They do not fit a hierarchical distribution or learn cross-month pooling. No regression coefficients, trees, or networks are involved.

    On the predeclared primary evaluation cohort (January 2015 through December 2025, 132 monthly events, 85 realized YES outcomes), the frozen results are: overall-model Brier 0.230314 and log loss 0.653345; seasonal-model Brier 0.032459 and log loss 0.130672 — a large, one-directional improvement for the calendar-aware model on this particular real, physically seasonal quantity. A predeclared sensitivity check that conservatively excludes the December 2022-August 2023 window affected by the post-eruption Mauna Kea measurement relocation, leaving 123 events with 79 YES outcomes and models refit on the reduced admitted history, shows the same pattern: overall Brier 0.230757 and seasonal Brier 0.034709. The seasonal model's advantage is not an artifact of the excluded months.

    Read this result for exactly what it licenses and no further. It shows that a real, strongly seasonal physical process (atmospheric CO2's well-known annual cycle) is, unsurprisingly, forecast better by a model that uses calendar information than by one that does not — a legitimate, disclosed, real-data finding about this series. It does not show that a real prediction-market question with different underlying dynamics would exhibit similar seasonal structure, does not compare against any executable market price, computes no fees, spread, or profit-and-loss figure, and does not establish availability at any verified historical publication time: the study's admission clock is an explicitly hypothetical retrospective convention layered onto a mutable, current-vintage NOAA extract, precisely the vintage-versus-availability distinction this chapter has emphasized throughout. A chronological, calendar-aware split of that data, however carefully constructed, still cannot recover the historical vintage — the values as they actually stood — at each past decision date, because only the current, possibly revised, extract is available for download today. See the data feasibility assessment for the full provenance and rights discussion behind the extract itself.

    13.8 Failure modes¶

    Treating repeated snapshots as independent trials overstates independent outcome information; use a declared horizon or an explicitly grouped multi-horizon evaluation. A variance-weighted average is not automatically a Bayesian state update: verify unbiasedness, covariance, and any assumed distribution. A Gaussian state can misrepresent bounded probability uncertainty, although a convex average of valid probabilities remains valid. Survival models require actual time-to-event and censoring definitions; a binary label alone cannot supply them. A detected changepoint is not causal proof. Finally, date-ordering a current-vintage series does not reconstruct historical vintages or establish past input availability.

    Exercises and solution sketches¶

    Exercise 1: a two-step Bayesian chain¶

    Starting from \(p_0=0.30\), apply a first update with likelihoods \(0.70\) (given \(Y=1\)) and \(0.40\) (given \(Y=0\)), then a second update with likelihoods \(0.65\) and \(0.45\). Compute \(p_1\) and \(p_2\).

    Solution sketch. \(p_1 = 0.30(0.70)/[0.30(0.70)+0.70(0.40)] = 0.210/0.490 = 0.428571\). \(p_2 = 0.428571(0.65)/[0.428571(0.65)+0.571429(0.45)] = 0.278571/0.535714 = 0.520000\).

    Exercise 2: a variance-weighted combination¶

    A prior estimate is \(m_0=0.55\) with variance \(v_0=0.04\); a new observation is \(z=0.62\) with variance \(r=0.01\). Compute the gain \(K\), the updated estimate \(m_1\), and the updated variance \(v_1\).

    Solution sketch. \(K=0.04/(0.04+0.01)=0.8\). \(m_1=0.55+0.8(0.62-0.55)=0.606\). \(v_1=(1-0.8)(0.04)=0.008\), smaller than either input variance because combining two independent estimates reduces uncertainty.

    Exercise 3: reading the companion's two-snapshot output¶

    The companion reports logistic probabilities of 0.258916 at a 12-hour horizon and 0.258227 at a 3-hour horizon for the same event. A colleague proposes scoring both as separate test observations to "get more data." Explain what is wrong with that proposal.

    Solution sketch. Both snapshots belong to a single event with one eventual outcome label; scoring both as separate observations would let that one outcome be counted twice in an aggregate score, inflating apparent sample size and potentially overweighting events observed more often than others. latest_per_event (or an equivalent explicit collapse) should reduce this to one row per event before any evaluation.

    Exercise 4: occurrence versus settlement¶

    A researcher wants to model "how many days until a contract's outcome is officially confirmed" using a proportional-hazards model, but instead trains it on the binary YES/NO label as if that label were a time-to-event target. Identify the specific conceptual error.

    Solution sketch. The proportional-hazards model is designed for a time-to-event target, not a binary outcome; feeding it a YES/NO label conflates "did the proposition occur" with "how long until settlement." The correct approach is either an ordinary binary-outcome model (Chapters 11–12) for the YES/NO question, or a genuine time-to-event target (actual settlement timestamps and a defined start time) if settlement delay is the real object of study — not both collapsed into one model.

    Exercise 5: a discrete hazard sanity check¶

    Given weekly hazard rates \(0.10, 0.15, 0.20, 0.25\) for four weeks, compute the probability of the event occurring in each week and the probability it has not occurred by the end of week 4. Confirm the four occurrence probabilities plus the remaining-survival probability sum to 1.

    Solution sketch. Week 1: \(0.100000\). Week 2: \((1-0.10)(0.15)=0.135000\). Week 3: \((1-0.10)(1-0.15)(0.20)=0.153000\). Week 4: \((1-0.10)(1-0.15)(1-0.20)(0.25)=0.153000\). Remaining survival: \((1-0.10)(1-0.15)(1-0.20)(1-0.25)=0.459000\). Sum: \(0.100000+0.135000+0.153000+0.153000+0.459000=1.000000\), confirming the bookkeeping is consistent.
