    11. Transparent statistical baselines¶

    Prerequisites¶

    You should be comfortable with conditional probability and Bayes' rule, the definitions of Brier score and natural-log loss, and the point-in-time discipline built across the data part of this book: decision cutoffs, label-availability cutoffs, and grouped chronological splits that keep an event's repeated snapshots on one side of a split. Chapter 10's forecast-evaluation material is assumed rather than repeated. The notation registry fixes the symbols \(\hat p\), \(x\), \(\beta\), \(\lambda\), and \(n\) used below; keep the registry open while reading.

    Learning objectives¶

    By the end of this chapter you should be able to: derive logistic regression as maximum-likelihood fitting of a log-odds-linear model and show why that likelihood is the same quantity as log loss; explain ridge and lasso penalties as constrained or penalized likelihood and connect them to specific Bayesian priors; explain what partial pooling buys you when many event families each have too few labeled outcomes to fit separately; and state, precisely, why a model's posterior interval or penalty choice is not a guarantee against misspecification, leakage, or an unrepresentative sample.

    11.1 Why start with a baseline you can fully explain¶

    A prediction-market forecasting project is tempting to start with the most flexible model available. This book starts somewhere else: with a model whose every coefficient can be inspected, whose likelihood is an explicit function you can write on one line, and whose failure modes are well understood. That choice is not conservatism for its own sake. A transparent baseline gives you a number to beat, a diagnosis tool when a fancier model disagrees with it, and a fallback when data are too thin for anything more elaborate to be trustworthy.

    "Too thin" is the ordinary condition in this domain, not an edge case. A recurring weekly question template might generate a few dozen resolved events per year. A one-off contract generates exactly one label, ever. Compare that to a typical supervised-learning benchmark with millions of rows, and the difference in what a model is entitled to claim becomes stark. Chapter 7 already established that dependence groups, not raw rows, are the currency of sample size here; this chapter is about models that respect that currency honestly.

    The companion script for this chapter, forecast_models.py, fits a plain logistic-regression baseline (this chapter), a boosted-tree model with held-out calibration (Chapter 12), and inspects the same fitted logistic model at two snapshots of one event (Chapter 13). Run it from the companion project root (book\companion):

    Command working directory: run this chapter's Python commands from book\companion. From the trading repository root, run Set-Location book\companion once first. The .venv belongs to that companion project; see companion setup.

    .\.venv\Scripts\python.exe examples\forecast_models.py

    Its fixture is generate_recurring, an invented threshold-like process with 180 synthetic events, each observed at two decision times before a single resolution. Every EventRow carries exactly three numeric features available at its own decision time: signal, horizon_hours, and market_probability. There is no fourth feature quietly smuggled in. The chapter's arithmetic below is worked by hand and checked with a small script, independent of that fixture, so you can follow the algebra without running anything.

    11.2 From odds to a linear model: deriving logistic regression¶

    Start from a question a decision-maker actually asks: given a feature vector \(x\), what probability should I assign to \(Y=1\)? A convenient way to guarantee an output between 0 and 1 without clipping is to model the log-odds as a linear function of \(x\):

    \[ \log\frac{\hat p}{1-\hat p} = \beta_0 + \beta_1 x_1 + \cdots + \beta_k x_k . \]

    Solving for \(\hat p\) gives the logistic (sigmoid) function of the linear score \(z=\beta_0+\sum_j \beta_j x_j\):

    \[ \hat p = \sigma(z) = \frac{1}{1+e^{-z}}. \]

    Two sanity checks are worth doing once rather than trusting from memory. As \(z\to -\infty\), \(e^{-z}\to\infty\), so \(\hat p\to 0\); as \(z\to\infty\), \(\hat p\to 1\); at \(z=0\), \(\hat p=0.5\). A concrete point: with \(\beta_0=-0.5\), \(\beta_1=1.4\), and \(x=0.9\), \(z = -0.5+1.4(0.9)=0.76\), and \(\sigma(0.76)=0.681354\) (five out of six decimal places checked with a script; report the number you actually computed, not a memorized constant).

    Now ask how to choose \(\beta\). The natural criterion is: pick the coefficients that make the observed outcomes as probable as possible under this model. For \(n\) independent-given-\(x\) observations, the likelihood is

    \[ L(\beta) = \prod_{i=1}^n \hat p_i^{\,y_i}(1-\hat p_i)^{1-y_i}. \]

    Taking the log (monotone, so it does not change the maximizer) and negating (so we can minimize instead of maximize) gives

    \[ -\log L(\beta) = -\sum_{i=1}^n \big[y_i\log \hat p_i + (1-y_i)\log(1-\hat p_i)\big]. \]

    Divide by \(n\) and you have exactly the book's log-loss formula from notation.md. This is not a coincidence dressed up as one: fitting a logistic regression by maximum likelihood is the same optimization as minimizing average log loss on the training data. The forecasting evaluation criterion from Chapter 10 and the fitting criterion in this chapter are the same function, evaluated on different samples with different purposes. That identity is worth internalizing, because it explains why a logistic model's training log loss is usually optimistic: the coefficients were chosen specifically to make the training log loss small.

    A single-observation numeric check makes the two loss terms concrete. With \(\hat p=0.681354\): if \(y=1\), the loss contribution is \(-\log(0.681354)=0.383674\); if \(y=0\), it is \(-\log(1-0.681354)=1.143674\). The asymmetry matters for teaching: a model that assigns high probability to an outcome that fails to occur is charged much more than a small miss near \(\hat p=0.5\), exactly reflecting the convexity of \(-\log(\cdot)\).

    Fitting generally uses an iterative numerical optimizer, not a closed-form coefficient solution. The companion standardizes features using training rows only, then calls scikit-learn's regularized LogisticRegression. Scaling changes the relative strength of a coefficient penalty and can improve numerical conditioning. Without regularization, rescaling a feature can be offset by inversely rescaling its coefficient; a large numeric range does not inherently make it dominate the fitted score. Refitting the scaler on validation or test rows would nevertheless use their distribution to alter an otherwise training-only pipeline.

    11.3 Regularization as a first-principles idea, not a knob¶

    A maximum-likelihood fit with many candidate features and modest sample size can overfit sharply, and it can fail outright under complete separation: if some linear combination of features perfectly predicts every training outcome, the unpenalized likelihood is maximized by coefficients that grow without bound, and the optimizer either fails to converge or reports an unstable, absurdly confident model. Regularization addresses both problems by adding a penalty on the size of \(\beta\) to the objective being minimized.

    Ridge (L2) regularization minimizes

    \[ -\log L(\beta) + \lambda \sum_j \beta_j^2 . \]

    To see where this comes from without appealing to a black box, consider the simplest possible case: ordinary least-squares fitting of \(y \approx \beta x\) from three points \((1,0.8)\), \((2,1.7)\), \((3,2.9)\), penalized the same way. Minimizing \(\sum_i(y_i-\beta x_i)^2+\lambda\beta^2\) over the scalar \(\beta\) has a closed form, \(\hat\beta=\dfrac{\sum_i x_iy_i}{\sum_i x_i^2+\lambda}\). Plugging in the three points gives \(\hat\beta=0.921429\) at \(\lambda=0\) (the unpenalized least-squares slope), \(0.860000\) at \(\lambda=1\), and \(0.678947\) at \(\lambda=5\) (values checked with a script). As \(\lambda\) grows, the fitted slope shrinks toward zero. That is the entire mechanism of ridge regularization laid bare in a case simple enough to compute by hand: it trades a small increase in fit-to-data error for a reduction in coefficient magnitude, which typically reduces the variance of the fitted coefficient across resamples at the cost of a small bias. The logistic case has the identical shrinkage intuition, without a closed form for \(\beta\).

    Lasso (L1) regularization minimizes \(-\log L(\beta)+\lambda\sum_j|\beta_j|\). Because the absolute-value penalty has a kink at zero, the optimum can land exactly at \(\beta_j=0\) for some coefficients, which ridge's smooth quadratic penalty essentially never produces exactly. TIBSHIRANI1996 proposes this constrained least-squares formulation and demonstrates that it can produce exact zeros; the original abstract's primary setting is linear regression, and its extension to sparse feature selection is a genuinely useful property, not proof that a selected feature is causally relevant to the underlying event. A coefficient of exactly zero says "this feature did not help the penalized fit criterion here"; it does not certify the feature is irrelevant to the real-world process, nor does it survive automatically to a different sample or period.

    Elastic net blends the two penalties, \(\lambda\big(\alpha\sum_j|\beta_j| + (1-\alpha)\sum_j\beta_j^2\big)\), and coordinate-descent methods can fit the resulting penalized path efficiently across linear, logistic, and multinomial models. FRIEDMAN2010 documents this computational machinery; it is a statement about how efficiently a penalized path can be computed, not a statement that any particular penalty improves this book's forecasting task. Choosing \(\lambda\) and \(\alpha\) is a model-selection decision like any other, and it must be made using only training and validation rows under the same point-in-time and dependence-group constraints as everything else in this book — never by peeking at test-period outcomes.

    11.4 A Bayesian view of the same problem¶

    Ridge regularization has an exact Bayesian reading: minimizing \(-\log L(\beta)+\lambda\sum_j\beta_j^2\) is equivalent to maximizing the posterior \(\propto L(\beta)\cdot p(\beta)\) under an independent Gaussian prior on each \(\beta_j\) with variance inversely related to \(\lambda\). GELMAN2008 argues for a related but more deliberately chosen default: scale predictors to a comparable range and place independent Student-t priors (heavier-tailed than Gaussian) on logistic-regression coefficients, motivated specifically by the complete-separation failure described above. A heavier-tailed prior still shrinks implausibly large coefficients toward zero, while assigning more prior mass to moderately large values than a Gaussian would, which the paper's abstract argues behaves more gracefully when separation is nearly exact. This is a proposed default, not a provably optimal choice for every dataset; treat it as a documented, reasonable starting point that still requires checking against your own data and priorities.

    The Bayesian framing changes what output one can seek. A penalized optimizer with a Bayesian interpretation supplies a posterior mode, not the full posterior or a credible interval automatically. Full Bayesian inference instead represents the posterior distribution over \(\beta\) and the induced uncertainty in predictions. The bayes_update helper illustrates prior-times-likelihood normalization for a binary hypothesis; it does not fit Bayesian logistic coefficients. Posterior computation for logistic regression generally needs numerical integration or sampling/approximation machinery, none of which this companion implements.

    The important caution, worth stating plainly because it is easy to elide: a posterior credible interval quantifies uncertainty conditional on the model and prior being adequate. It does not, by itself, guarantee protection against misspecification. If the true relationship between features and outcome is not close to the logistic form, if there is unmodeled dependence between "independent" observations, or if the training period does not resemble the evaluation period, a narrow credible interval can be confidently wrong. Bayesian machinery formalizes uncertainty within a stated model; it does not verify that the stated model is the right one.

    11.5 Partial pooling: what to do with too few labels per group¶

    Prediction markets often arrive in families: many structurally similar but not identical recurring questions (a weekly threshold contract, a recurring economic-release question), each with only a handful of resolved events. Two naive strategies bound the useful range. Complete pooling ignores family identity and fits one model on all events, which discards genuine differences between families. No pooling fits a separate model per family, which for a family with, say, six resolved events produces an estimate with enormous sampling variance; a family that happened to see 4 of 6 events resolve YES gets a raw rate of \(4/6=0.666667\), and that number is barely more informative than the coin flip that produced it.

    Partial pooling is the compromise: shrink each family's raw estimate toward a shared reference (such as the overall base rate across families) by an amount that depends on how much data that family actually has. A simple, fully worked instance of the idea, before any hierarchical-model machinery, is a Beta-Binomial shrinkage estimate: if a family has \(n\) observed events with \(s\) successes, and the shared reference rate across families is \(\bar p\), then

    \[ \tilde p = \frac{s + k\bar p}{n+k} \]

    for a prior-strength parameter \(k\) that can be read as "worth \(k\) pseudo-observations of the reference rate." With \(n=6\), \(s=4\), \(\bar p=0.40\): at \(k=2\), \(\tilde p=(4+0.8)/8=0.600000\); at \(k=5\), \(\tilde p=(4+2.0)/11=0.545455\); at \(k=10\), \(\tilde p=(4+4.0)/16=0.500000\) (all checked with a script). As \(k\) grows, the family's own six observations are increasingly outweighed by the shared reference, pulling the estimate toward \(\bar p\). As \(n\) grows for a fixed \(k\), the family's own data dominates instead. That single formula is the entire idea behind hierarchical, partially pooled models: a family with little data borrows strength from the population; a family with abundant data is left mostly alone.

    A full hierarchical logistic regression generalizes this by placing a shared prior distribution on family-level intercepts (or coefficients) whose own parameters are estimated from all families jointly, so that the amount of pooling is itself learned from the data's between-family and within-family variance rather than fixed by hand. This book does not implement that joint estimation; the Beta-Binomial case above is presented because it is small enough to verify without unfamiliar software, and it isolates the mechanism (shrink more when the group's own information is scarce) that motivates the larger machinery. GELMAN2008 is again the relevant reading pointer for weakly informative priors in this style of model; it does not certify a specific choice of \(k\) or a specific pooling structure for prediction-market families, which remain modeling decisions you must justify from your own data and its actual group sizes.

    11.6 Sample and label constraints specific to this domain¶

    Two constraints recur across every model in this part of the book, and they apply to the plainest logistic baseline exactly as much as to anything more elaborate.

    First, repeated snapshots of the same event are not additional independent samples. The companion fixture deliberately generates two decision times per event; latest_per_event collapses these to one row per event before fitting or scoring specifically so that a single underlying outcome cannot be counted twice as evidence for or against a model. If you instead trained on both snapshots as if they were independent labeled examples, the fitted model would implicitly overweight events observed more often, and a model evaluated the same way could report artificially confident scores driven by duplicated labels rather than genuine sample size.

    Second, features must be available at each row's decision time; training labels must be available by the later model-fitting cutoff. Requiring labels at their own earlier prediction times would defeat forecasting. grouped_chronological_split raises for feature-late rows or inconsistent identities, but excludes whole groups that straddle boundaries or lack labels at the relevant cohort cutoff. The fitting pipeline separately rejects a supplied split that violates those constraints. The default result is 89 training events, 44 validation events used for the boosted calibrator, and 45 test events, with two groups purged. The cohort counts reflect both time and group availability, not an arbitrary division into equal thirds.

    11.7 Reading the companion's baseline output honestly¶

    Running forecast_models.py reports, on 45 test events: reference_rate Brier 0.249699 and log loss 0.692562; market_probability Brier 0.207439 and log loss 0.606343; and logistic Brier 0.198372 and log loss 0.582490. Logistic beats both baselines on this synthetic run. The generator makes the label probability logistic in an unobserved latent value, while the model receives a noisy signal, not that latent value itself. This construction makes predictive signal plausible but does not guarantee logistic specification is exact or that the fitted model wins on every finite test sample. The baselines make the observed comparison interpretable rather than self-congratulatory.

    Two things this comparison does not show are worth stating explicitly. It does not show that a logistic model beats a real market's own quoted probability, because market_probability here is a synthetic feature generated by the same toy process, not an executable, fee-inclusive price from an actual venue. And a single synthetic run with one random seed is not evidence of a stable advantage; the honest use of this script is to check that your pipeline behaves correctly under known ground truth, not to report its numbers as a discovered edge.

    11.8 Failure modes¶

    A regularized fit does not protect against a badly specified feature set: shrinking irrelevant coefficients toward zero is not the same as having included the relevant ones. Complete separation is easy to trigger accidentally with a rare categorical feature or a near-perfect proxy, and an unpenalized fit can silently report absurd coefficients rather than an error; always inspect fitted coefficient magnitudes, not just the reported score. Fitting a scaler, an imputer, or a feature-selection step on data that includes validation or test rows is leakage even if the model itself is later fit correctly on training rows only. Partial pooling can be pushed too far: an aggressive shared prior can erase a real difference between families that would have been visible with a more modest amount of shrinkage, and there is no shrinkage amount that is correct for every dataset. Finally, a Bayesian posterior interval answers "how uncertain am I within this model," not "how likely is this model to be the right one"; treating a narrow credible interval as proof against misspecification is a category error, not a subtle numerical one.

    Exercises and solution sketches¶

    Exercise 1: log-odds to probability¶

    A logistic model reports \(\beta_0=-0.5\), \(\beta_1=1.4\) for a single feature \(x\). Compute \(\hat p\) at \(x=0.9\), and at \(x=-0.9\). Which prediction is more confident, and why does the sign of \(x\) matter here?

    Solution sketch. At \(x=0.9\): \(z=0.76\), \(\hat p=\sigma(0.76)=0.681354\). At \(x=-0.9\): \(z=-0.5-1.26=-1.76\), \(\hat p=\sigma(-1.76)\approx 0.147\). The negative-\(x\) case is more confident (further from 0.5) because the same magnitude of \(\beta_1 x\) now reinforces the negative intercept rather than partly offsetting it; the model is not symmetric around \(x=0\) because \(\beta_0\neq0\).

    Exercise 2: ridge shrinkage by hand¶

    Using the three points \((1,0.8)\), \((2,1.7)\), \((3,2.9)\) and the scalar ridge formula \(\hat\beta=\frac{\sum x_iy_i}{\sum x_i^2+\lambda}\), compute \(\hat\beta\) at \(\lambda=0,1,5\) and describe the trend.

    Solution sketch. \(\sum x_iy_i=1(0.8)+2(1.7)+3(2.9)=12.9\); \(\sum x_i^2=1+4+9=14\). At \(\lambda=0\): \(12.9/14=0.921429\). At \(\lambda=1\): \(12.9/15=0.860000\). At \(\lambda=5\): \(12.9/19=0.678947\). The slope shrinks monotonically toward zero as \(\lambda\) grows, trading fit for coefficient magnitude.

    Exercise 3: partial pooling toward a reference rate¶

    A market family has \(n=6\) resolved events with \(s=4\) successes; the shared reference rate is \(\bar p=0.40\). Compute the shrunk estimate at prior strengths \(k=2\) and \(k=10\), and explain in one sentence why the raw rate \(4/6\) might be misleading here.

    Solution sketch. At \(k=2\): \((4+0.8)/8=0.600000\). At \(k=10\): \((4+4.0)/16=0.500000\). The raw rate of \(0.666667\) is based on only six outcomes, so its sampling variance is large; shrinkage trades some of that noise for a controlled bias toward the reference rate, and the appropriate \(k\) should reflect how similar you believe this family genuinely is to the reference population, not be chosen to produce a preferred answer.

    Exercise 4: separating fitting loss from evaluation loss¶

    Explain why a logistic model's log loss computed on its own training data is generally an optimistic estimate of the log loss it will achieve on a properly held-out, event-grouped test period, even before considering any leakage bug.

    Solution sketch. The coefficients were chosen specifically to minimize the training log loss (Section 11.2's identity between maximum likelihood and log loss), so the training score reflects both genuine signal and fitting to that particular sample's noise. A held-out score, computed on events whose labels played no role in choosing \(\beta\), does not benefit from that fitting-to-noise effect and is the honest number to report, provided the split also respects event grouping and label availability.

    Exercise 5: reading the companion's Brier numbers¶

    The companion script reports reference_rate Brier 0.249699, market_probability Brier 0.207439, and logistic Brier 0.198372 on 45 test events. Is this comparison evidence that logistic regression outperforms real market prices in general?

    Solution sketch. No. market_probability here is a feature generated by the same synthetic process used to generate the labels, not an executable price from an actual venue, and the entire exercise runs on one seeded synthetic sample. The comparison is a correctness check on the pipeline (does a model with access to the true signal beat naive baselines under known ground truth), not a market-beating claim, and it says nothing about a real venue's price efficiency.
