    27. Build an event-driven forecasting workflow¶

    Prerequisites¶

    You should have already run the pattern quickstart in Chapter 26 and understand its evidence gate. You need the forecast-evaluation material from Chapter 10, the sequential-forecast discussion in Chapter 13, the combination methods in Chapter 16, and the paper-decision machinery from Chapters 17 and 24, particularly PaperInputs, RiskBudget, and paper_decision. Keep the notation registry's distinction between event time, publication time, observation time, and decision time close at hand; this chapter depends on all four staying separate.

    Learning objectives¶

    By the end of this chapter you should be able to run a single recurring event through an already-fitted forecaster, correctly distinguish the event's own historical timestamps from a newly invented quote time attached only for this chapter's arithmetic, explain why both example order books in this quickstart produce NO_TRADE, and state exactly why that is the correct, honest outcome rather than a demonstration failure. You should also be able to explain how this quickstart's synthetic books differ from the real, current-vintage NOAA study introduced in Chapter 26, and why neither one supplies price, fee, or queue evidence for any real venue.

    27.1 A concrete goal: one event, one forecast, two quotes¶

    This chapter's script picks a single held-out event, generates a forecast for it using an already-fitted model, and then checks that forecast against two different hypothetical order books to see whether either would clear a simple cost-and-budget screen. From the companion project root (book\companion), after the setup described in Chapter 26:

    Command working directory: run this chapter's Python commands from book\companion. From the trading repository root, run Set-Location book\companion once first. The .venv belongs to that companion project; see companion setup.

    .\.venv\Scripts\python.exe examples\quickstart_event.py

    Open examples/quickstart_event.py while you read this chapter. It calls fit_forecaster(split) on the same teaching_split used in Chapter 26, then selects latest_per_event(split.test)[0], the chronologically first held-out event by decision time. On this checkout that event is toy-0135.

    27.2 Reading the actual output¶

    The observed run includes the following excerpt (some wrapper and explanatory fields are omitted):

    {
  "result": {
    "source_event": "toy-0135",
    "feature_publication": "2025-05-16T14:50:00+00:00",
    "feature_observation": "2025-05-16T14:58:00+00:00",
    "historical_decision": "2025-05-16T15:00:00+00:00",
    "forecast": 0.200542,
    "new_synthetic_quote_time": "2025-07-01T12:00:00+00:00",
    "illustrative_screen": {
      "status": "NO_TRADE", "quantity": 0,
      "executable_cost": "4.10", "modeled_expected_profit": "-2.094580",
      "reason": "modeled edge does not exceed the stated cost buffer"
    },
    "costly_no_trade": {
      "status": "NO_TRADE", "quantity": 0,
      "executable_cost": "9.60", "modeled_expected_profit": "-7.594580",
      "reason": "modeled edge does not exceed the stated cost buffer"
    },
    "evidence_gate": {"status": "REJECT_LIVE_EDGE_INFERENCE"}
  }
}

    Four timestamps appear, and they mean different things. feature_publication at 14:50 UTC is when the invented upstream bulletin for this event was notionally released. feature_observation at 14:58 UTC is when the model's inputs became available to a decision process. historical_decision at 15:00 UTC is the timestamp the fixture generator originally attached to this event's decision point, back when toy-0135 was constructed. new_synthetic_quote_time, 2025-07-01T12:00:00Z, is a wholly different and much later timestamp: it is NOW from _support.py, attached only so this chapter's illustrative PaperBroker and order books have a valid, internally consistent clock to validate against. Do not read new_synthetic_quote_time as if it were a later observation of the same real historical order flow; it is a new invented moment purely for the arithmetic demonstration, more than a month after the event's own historical decision time.

    forecast is 0.200542, the fixed_equal_ensemble prediction from FittedForecaster.predict, an equal blend of a logistic model and a validation-calibrated boosted model, rounded to six decimal places only for this printed display. The rounding note in the output is important: "six decimals for this printed arithmetic; scoring uses unrounded model probabilities". Any evaluation elsewhere in the companion uses the full-precision value; the six-decimal figure shown here exists only so the arithmetic below is checkable by hand.

    27.3 Walking through the arithmetic behind both no-trade decisions¶

    The script builds two invented order books using _support.book(): a "cheap" book with ask 0.40, and a "costly" book, labeled expensive, with bid 0.90 and ask 0.95. Both are passed through PaperInputs and screened by paper_decision, which in turn calls screen_buy_yes from prediction_market_lab.risk. Before doing so, paper_decision first asks the broker for its own remaining_book view of whichever quote it was handed, not the raw snapshot as supplied: any depth this same broker has already consumed against that identical snapshot in an earlier fill is subtracted out first, so a level a prior order already swept cannot silently reappear and be sized against a second time. Both books in this script are freshly constructed and have never had any depth consumed against them by this broker, so the remaining view here is identical to the quote as constructed, and the arithmetic below is unaffected; this consumed-liquidity accounting matters more once a broker has already taken from the very same book snapshot it is being screened against.

    For the cheap book, buying 10 YES units at an ask of 0.40 with the fixture's flat USD 0.01 per-unit fee costs \(10 \times (0.40 + 0.01) = 4.10\), exactly the canonical executable_cost shown. The model-conditional expected profit is \(10 \times 0.200542 - 4.10 = 2.00542 - 4.10 = -2.09458\), rounded to -2.094580 in the printed decimal string. Because the model assigns this event only a 20 percent chance of resolving YES, the expected value of paying 41 cents per unit including fees is sharply negative; the screen correctly reports NO_TRADE with the reason "modeled edge does not exceed the stated cost buffer".

    For the costly book, the ask is 0.95, so the same ten units cost \(10 \times (0.95 + 0.01) = 9.60\), and the modeled expected profit is \(10 \times 0.200542 - 9.60 = -7.59458\). This is an even worse trade, for the obvious reason that the price is higher while the forecast has not changed. Both screens reject the trade for the identical stated reason, which is exactly what a coherent risk screen should do: a forecast well below the executable price produces NO_TRADE whether the price is moderately or severely unfavorable, and the size of the negative modeled edge, not just its sign, is preserved in the output so a reader can see how far the quote was from being attractive.

    Do not treat the no-trade result as a defect. Replacing these quotes after seeing the result and presenting the replacement as the original experiment would hide selection. A separately labeled hypothetical sensitivity exercise is legitimate, as Section 27.5 shows. The original two books both cost more than the roughly 0.20 forecast supports, and that unfavorable result must remain visible.

    27.4 Why the forecast is a blend, not a single model's raw output¶

    The 0.200542 figure is fixed_equal_ensemble, not one model's raw output. Chapter 16 explains why combining probabilities is a modeling choice rather than an automatic improvement. Gneiting and Raftery's inspected scoring treatment supplies the propriety framework; its categorical quadratic convention must be reversed from reward to loss and divided by two for this book's single-YES score. GNEITING2007 Bates and Granger's inspected abstract gives an empirical point-forecast combination example, while Gneiting and Ranjan study predictive-distribution combinations. Neither establishes that this fixed equal blend is optimal, calibrated, or profitable. BATES1969 GNEITING2013

    None of these three sources certifies that this particular equal-weight blend is optimal for this particular fixture, and the companion's own forecast_models.py observed results, quoted in the examples README, show a validation-calibrated boosted model alone scoring worse than an uncalibrated logistic model on this same held-out cohort, a reminder that a more elaborate combination or calibration step is not automatically an improvement. The equal-weight blend used in this script is a defensible, simple default precisely because it does not require estimating additional combination weights from the same data being evaluated; it is not a claim that this is the best possible combination for toy-0135 or for any other event.

    27.5 What the reader does next¶

    For a clearly labeled local sensitivity exercise, change the cheap book construction from book(ask="0.40") to book(bid="0.14", ask="0.15"), leaving the costly book unchanged. Changing only the ask would leave the default USD 0.38 bid above it and correctly raise ValueError("crossed book is ambiguous"). The valid hypothetical book costs \(10(0.15+0.01)=1.60\) and gives modeled expected profit \(10(0.200542)-1.60=0.40542\). With the unchanged fresh inputs, cash, and USD 5.00 budget, the screen returns PAPER_CANDIDATE_ONLY. Restore the example afterward and report the modified run as a sensitivity exercise, never as newly discovered evidence or a replacement for the original no-trade result.

    The script states that its hypothetical books are not joined to the historical event and cannot form a P&L backtest. The fixture supplies two dated feature snapshots for toy-0135, including a synthetic market forecast benchmark in each; prediction consumes the selected row's features even though model parameters are frozen. Neither row supplies the later executable books constructed here. Those books exist only to exercise the decision code at an invented clock. A historical execution claim would require actual as-of quotes and depth, not a newly manufactured book attached to an old forecast.

    27.6 Real current-vintage data versus this quickstart's synthetic books¶

    It is worth being precise about a distinction that is easy to blur: this chapter's event, forecast, and order books are entirely synthetic and illustrative, generated by prediction_market_lab.data.generate_recurring and _support.py, and none of the ensuing arithmetic represents anything that happened in the real world. The NOAA study introduced in Chapter 26 and detailed in experiments/README.md and experiments/protocol.json is different in kind, though not in trading relevance: it uses genuinely real, attributed atmospheric CO2 observations, under a predeclared and frozen protocol, with a hypothetical two-month admission lag standing in for an unverified historical publication clock.

    Both examples share an important limitation, and it is worth stating clearly rather than glossing over: neither supplies price, fee, or queue evidence for any real prediction-market venue. This chapter's order books are invented numbers chosen to exercise code paths; the NOAA study has no prediction-market contract, price, or fee of any kind attached to it at all, because its subject is monthly greenhouse-gas measurements, not an event-contract market. A reader who wants a current real venue quote can run the companion's optional, explicitly gated market_data snapshot collector, documented in data/README.md; it is not called by this or any other default script. Even its output is only a current public GET snapshot, not a historical order book, a fee/execution adapter, or a verified conversion into this book's classroom OrderBook. Building that fuller, validated venue pipeline remains the permission-gated, unimplemented future study described in the book's data-feasibility assessment, and neither quickstart script performs it.

    27.7 Troubleshooting¶

    If the forecast differs, check fixture, model seed, Python, and dependency versions; a fixed seed is not a guarantee across every numerical-library build. paper_decision returns NO_TRADE when any supplied verification field is not the literal True; omitting a required PaperInputs constructor argument instead raises a construction error. Stale or mismatched books passed through the gate return stated no-trade reasons. Invalid book construction, such as a crossed bid/ask, can raise before the gate is called. Distinguish these stages when diagnosing a local modification.

    27.8 Exercises and solution sketches¶

    Exercise 1: recomputing the costly-book arithmetic¶

    Using the values printed in Section 27.2, verify by hand that the costly book's modeled expected profit is -7.594580, and state what price would make this specific ten-unit trade break even given the same 0.200542 forecast and USD 0.01 fee.

    Solution sketch. Cost is \(10\times(0.95+0.01)=9.60\); expected value is \(10\times0.200542-9.60=2.00542-9.60=-7.59458\), matching the printed figure. For break-even, solve \(10p - 10(a+0.01) = 0\) for the ask \(a\) given \(p=0.200542\): \(a = p - 0.01 = 0.190542\). Only an ask at or below about 0.19 would make this particular quantity's modeled expected value nonnegative before any risk-budget check.

    Exercise 2: why quantity is zero rather than a smaller positive number¶

    Both screens report quantity: 0. Explain why the screen does not instead try a smaller quantity, such as one or two units, to see if a smaller trade clears the cost buffer.

    Solution sketch. The sign of the modeled expected profit per unit does not depend on quantity in this flat-fee, constant-price construction: each additional unit contributes the same \(p - (a+f)\) margin, so if that per-unit margin is negative, no quantity, large or small, produces a nonnegative expected value. screen_buy_yes correctly reports the requested quantity as rejected outright rather than searching for some other quantity that might happen to look better.

    Exercise 3: separating the fitted forecast from the quote time¶

    A colleague argues that because new_synthetic_quote_time is more than a month after historical_decision, the forecast must be "stale" and should be refit before use. Evaluate this argument.

    Solution sketch. The forecast is a fixed function of the event's own features, computed once by an already-fitted model at prediction time; it does not depend on which later clock timestamp is used to validate an unrelated order book. The real concern is different: attaching a much later quote time to an old forecast is only valid as an illustrative accounting exercise, precisely because the quote itself has no relationship to the historical event. It would be a modeling error to imply the forecast was made using information available at the later quote time, which is why the script's limitation field flags this boundary explicitly rather than leaving it implicit.

    Exercise 4: constructing a scenario that would pass the risk budget too¶

    Suppose an ask of 0.15 produces a positive modeled expected profit, as in Section 27.5's edit. Explain what additional check, beyond a positive expected value, screen_buy_yes still applies before returning PAPER_CANDIDATE_ONLY, and why that check exists separately from the cost comparison.

    Solution sketch. screen_buy_yes also calls budget.permits(...), comparing the order's cost and reserve against RiskBudget.max_order_cost and max_committed_cash, together with the broker's currently available and already-committed cash. A positive modeled expected value describes an attractive bet in isolation; it says nothing about whether the trader has enough uncommitted capital, or whether taking this position would push total committed cash past an explicit risk limit. Chapter 29 shows a case where a positive modeled expected profit is still rejected for exactly this second reason.

    Exercise 5: why an equal blend is not the same claim as an optimal blend¶

    A reader proposes replacing the fixed equal-weight blend with weights chosen to minimize Brier score on the same 45-event test cohort used to report results throughout this part of the book. Explain what would go wrong with reporting that reweighted blend's score as this chapter's result.

    Solution sketch. Choosing combination weights by minimizing error on the very cohort being used for the headline evaluation is a form of fitting on the test set: the resulting score would no longer describe an untouched evaluation in the sense Chapter 19 requires, even though no traditional model-training step touched that data. Weight selection is itself a decision that needs its own held-out data or a predeclared fixed rule, such as the equal weighting actually used here, precisely to avoid quietly inflating the reported score through cohort-specific tuning.
