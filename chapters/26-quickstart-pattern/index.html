    26. Investigate your first simple pattern¶

    Prerequisites¶

    You should already be comfortable with the exploration discipline of Chapter 9, the proper-scoring-rule and calibration material of Chapter 10, and the evidence-after-search reasoning of Chapter 19. Chapter 25's falsifiable-hypothesis discipline is the direct predecessor to this one. You should know what a dependence group is, why a chronological split is not automatically an independence guarantee, and why the single-YES Brier convention in the notation registry is the one this book always reports.

    Learning objectives¶

    By the end of this chapter you should be able to run the pattern quickstart from a clean checkout, read its JSON output correctly, and explain in your own words why two fixed probability bins inspected once are a different kind of evidence than the same two numbers found after trying many bins. You should be able to distinguish a post-hoc diagnostic from a predeclared confirmatory comparison, explain why this script's evidence_gate always rejects a live-edge inference regardless of how attractive its numbers look, and optionally run the book's one real-data forecasting exercise well enough to state exactly what it does and does not show.

    26.1 A concrete goal and a clean setup¶

    The goal of this chapter is narrow and deliberately unglamorous: run one already-written script, read its output line by line, and understand exactly what kind of evidence it does and does not supply. That habit, applied consistently, is worth more than any individual technique in the preceding chapters. From the companion project root (book\companion), with a fresh shell:

    Command working directory: run this chapter's Python commands from book\companion. From the trading repository root, run Set-Location book\companion once first. The .venv belongs to that companion project; see companion setup.

    python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install -e . --no-deps

    The first command creates a virtual environment. The second installs version-pinned runtime dependencies, not hash-locked wheels; requirements.lock is a version lock, and platform wheels, numerical-library builds, and the build backend are not frozen by it. The third installs prediction_market_lab in editable mode without resolving its runtime dependencies again. Installation may download packages, but requires no trading account, API key, GPU, or paid model. After installation all default examples run offline. The documented environment supports numerical reproduction; bit-for-bit portability across every platform is not promised.

    Now run the script this chapter is about:

    .\.venv\Scripts\python.exe examples\quickstart_pattern.py

    26.2 Reading the actual output¶

    The script prints one JSON object. This excerpt selects central fields from the observed Python 3.12.6 run; additional labels, reasons, and boundary fields remain in the full output:

    {
  "data": "SYNTHETIC / ILLUSTRATIVE",
  "result": {
    "groups": {
      "market_below_half": {
        "events": 30,
        "observed_yes_rate": 0.333333,
        "market_brier": 0.223735,
        "training_reference_brier": 0.274418
      },
      "market_at_least_half": {
        "events": 15,
        "observed_yes_rate": 0.933333,
        "market_brier": 0.174846,
        "training_reference_brier": 0.200261
      }
    },
    "no_trade_baseline_profit": "0.00",
    "evidence_gate": {"status": "REJECT_LIVE_EDGE_INFERENCE", "eligible_for_research_review": false}
  }
}

    Read the numbers in order rather than jumping straight to the Brier scores. There are 45 held-out test events in total, split by whether the synthetic market's own quoted probability was below one-half (30 events) or at least one-half (15 events). Within each bin, observed_yes_rate is simply the fraction of those events whose eventual binary label was YES: 0.333333 in the low bin, 0.933333 in the high bin. market_brier scores the synthetic market's own quoted probability against that realized label using the single-YES convention from the notation registry; training_reference_brier scores a single constant reference rate, estimated only from the training cohort, against the same realized labels. In this toy run, the market's own quoted number scores better than the flat training-derived reference in both bins, which is unsurprising: the invented market probability in this fixture was constructed, by the generator in prediction_market_lab.data.generate_recurring, to correlate with the same latent signal that drives the outcome. That correlation is a property of the synthetic fixture, not a discovery about any real venue.

    no_trade_baseline_profit is the constant string "0.00". This script places no order of any kind; the field exists only to make explicit, at every stage, that reading these numbers is not the same activity as trading on them. evidence_gate reports REJECT_LIVE_EDGE_INFERENCE with eligible_for_research_review set to false. This is not a bug to route around. It is the correct answer for any all-synthetic input, and Section 26.4 explains exactly why the gate is built that way.

    26.3 What the reader does next: reading the code, not just the output¶

    Open examples/quickstart_pattern.py alongside the printed output. The script calls teaching_split(recurring()) from _support.py, which loads the fixed fixture at data/fixtures/recurring_events.csv through prediction_market_lab.data.load_recurring and then applies grouped_chronological_split with three predetermined cutoffs baked into teaching_split. It then takes latest_per_event of the resulting test cohort, which keeps exactly one decision-time snapshot per event, chosen by its latest decision_at timestamp, so that the two snapshots a single recurring event contributes are never both counted as if they were independent test rows.

    The script fixes two bins, market_probability >= 0.5 or not, and performs no threshold search during execution. That makes the run reproducible, but fixed source code alone does not prove a choice preceded all author inspection. Trying many cutoffs and reporting only the most striking one would add selection bias. Treat this repeatedly inspected synthetic fixture as a demonstration of how to specify a comparison, not as untouched confirmatory evidence.

    The script deliberately reports no p-value or confidence interval. Its 45 rows are one latest snapshot from each of 45 separately generated events; sharing a generator family does not itself make distinct events dependent. The two original snapshots within each event do share a latent value and label. One could analyze simulation uncertainty under that stated generator, but it would still be uncertainty about an invented process, not evidence of market performance. This quickstart reports descriptive scores rather than claiming either a real-market interval or more independent outcomes than were generated.

    26.4 Distinguishing post-hoc diagnostics from predeclared confirmatory discovery¶

    A post-hoc diagnostic inspects data after the fact to generate candidate explanations: "the market's quoted probability seems informative when it is extreme," or "recorded rates in this bin look higher than I expected." This is a legitimate and useful step in exploratory work; Chapter 9 dedicates an entire chapter to doing it honestly. But a diagnostic observation earns no claim of confirmed discovery by itself. It has not been checked against data that could not have influenced its own formulation, and it has not accounted for how many other candidate patterns were silently considered and discarded before this one was noticed.

    A predeclared confirmatory comparison fixes its cohort, bins, metric, and procedure before relevant inspection can shape those choices, then reports the result whether favorable or not. This quickstart demonstrates that procedural shape, but its authors constructed and repeatedly inspected the fixture. It is not a confirmatory discovery, even if the current code has only one threshold. Confirmatory status depends on the actual research history, not merely on a constant appearing in a script.

    The practical failure mode to watch for in your own later work is silent bin curation: running the analysis once, not liking the result, adjusting a cutoff, a fixture parameter, or an inclusion rule, and running it again, without recording that the first attempt happened. Each such adjustment, even an apparently reasonable one like excluding an inconvenient outlier month, is a trial. A trial log, as Chapter 19 describes, is the only defense against later mistaking a best-of-several result for a first and only look.

    Three qualified statistical tools bear directly on how this discipline scales past a single fixed comparison, and it is worth naming what each one does and does not repair, rather than treating "predeclare it" as a slogan that makes every subsequent statistic automatically trustworthy. White's reality check addresses whether the single best rule out of an entire searched family could plausibly have arisen by chance given the whole family considered, under a specific bootstrap construction whose stationary-data assumptions require checking against your own data before relying on it. WHITE2000 The Benjamini-Hochberg false discovery rate procedure addresses a related but distinct question, controlling the expected proportion of false rejections across many simultaneously tested hypotheses, and it still requires a well-defined test family and valid input significance values to mean what it claims. BENJAMINI1995 Bailey, Borwein, Lopez de Prado, and Zhu's backtest-overfitting framework targets a third question again, the probability that a reported strategy selection reflects overfitting from repeated holdout inspection during the research process itself, rather than genuine out-of-sample skill. BAILEY2017 None of these three tools, individually or together, cures an event-group leak, an unavailable label used as if it were available, or a cost assumption that turns out to be wrong; they qualify a search process's own statistics, not the underlying data discipline this book spends its first eight chapters establishing.

    26.5 An optional real-data exercise: the frozen NOAA study¶

    Everything in Sections 26.1 through 26.4 uses an invented fixture. This section describes an optional exercise using genuinely real observational data, so you can see the difference in evidentiary weight directly, not just read about it. The research feasibility assessment and the experiments README explain the full protocol; this section summarizes what running it teaches.

    .\.venv\Scripts\python.exe experiments\noaa_study.py

    Do not pass --refresh-data or --replace-results. The plain command makes no network request and writes no files; it recomputes the study from the committed extract and verifies the frozen input and output bytes. The protocol was locally predeclared before acquisition or scoring; the results were frozen after that evaluation, not before their values existed. The following primary-result excerpt omits the subsequent paired-difference and sensitivity lines:

    VERIFIED OFFLINE (no files changed)
FINAL-VINTAGE retrospective teaching study; NOT a trading backtest.
primary: n=132, YES=85
  overall: Brier=0.230313524, log loss=0.653345440
  seasonal: Brier=0.032459388, log loss=0.130672065

    The 132 events are calendar target months from January 2015 through December 2025, each scoring whether that month's recorded Mauna Loa CO2 mean exceeded the immediately preceding month's mean, under the predeclared clock and Beta(1,1) models fixed in protocol.json. The overall model's Brier score of 0.230313524 reflects an expanding constant-rate forecast; the target-month seasonal model's 0.032459388 reflects a strong, well-known annual cycle in atmospheric CO2 concentration. This gap did not require any strategy search: the protocol, the training scheme, and the two candidate models were all fixed, in writing, before either score was computed, and the experiments README records the exact predeclaration and freeze timestamps. The same README also reports a predeclared 123-event sensitivity cohort, conservatively excluding the alternate-location Maunakea measurement period, which shows the same pattern (overall Brier 0.230757404, seasonal 0.034708546), together with a reproducible, no-plotting-dependency calibration figure; neither addition changes what this study can or cannot establish.

    Read this result for exactly what it is and nothing more. NOAA_CO2, NOAA_DATA, and NOAA_POLICY establish that these are real, attributed, public-domain government observations, not synthetic fixtures. NOAA_CO2 NOAA_DATA NOAA_POLICY They are also current-vintage data: the source file can be revised, and this study's clock is a hypothetical retrospective admission rule, not a verified historical publication timestamp. There are no prediction-market contracts, prices, fees, order books, or fills anywhere in this study. A forecast-scoring improvement on a recorded rise in atmospheric carbon dioxide is not evidence about pricing efficiency in any prediction market, and this book does not claim otherwise.

    26.6 Troubleshooting¶

    If creating .venv fails, check the supported Python 3.12 interpreter and directory permissions; do not delete an environment containing unrelated work. The runtime lock pins versions but contains no artifact hashes, so it is not itself a wheel-integrity check. Installation failures should be diagnosed from their actual messages, not bypassed by silently changing dependency versions. For ModuleNotFoundError, confirm the editable install and invoke .\.venv\Scripts\python.exe rather than an unrelated interpreter on PATH. If numerical output differs, record Python/package versions and platform details; do not change fixtures, seeds, or rounding merely to obtain the quoted result.

    If experiments\noaa_study.py reports a hash-verification failure instead of VERIFIED OFFLINE, do not "fix" it yourself by rewriting the flagged file's line endings, re-saving it in an editor, or passing --refresh-data/--replace-data/--freeze-results/--replace-results to make the check pass; the frozen hashes are bound to the exact original bytes of the data, protocol, source, and results files, and any of those actions can silently produce a different, unreviewed frozen artifact rather than reproducing the one this chapter quotes. A hash mismatch on an otherwise unmodified checkout is a checkout-integrity or repository-configuration question, not a data or environment problem for a reader to work around; report it and keep the checkout as received rather than normalizing, replacing, or re-encoding anything to make the numbers agree.

    26.7 Exercises and solution sketches¶

    Exercise 1: recomputing a bin's Brier score by hand¶

    Suppose a fixed bin contains three held-out events with market-quoted probabilities 0.60, 0.70, and 0.55, and realized labels YES, YES, NO. Compute the single-YES Brier score by hand.

    Solution sketch. Squared errors are \((0.60-1)^2=0.16\), \((0.70-1)^2=0.09\), and \((0.55-0)^2=0.3025\). The mean is \((0.16+0.09+0.3025)/3 = 0.184166\overline{6}\). Note that this toy bin has only three events; a bin this small would ordinarily be too sparse to support any confident interpretation on its own, which is one reason this chapter's fixture uses bins of 30 and 15 events instead.

    Exercise 2: why a third bin is not free to add later¶

    Suppose after seeing the two-bin result above, you notice the fixture also records a horizon_hours field and consider adding a third split by horizon to see if it produces an even larger score gap. Explain what is wrong with adding this comparison now, and what would make it acceptable.

    Solution sketch. It is acceptable as a clearly labeled additional exploratory comparison, recorded in the trial log. It is not an untouched confirmation of a new horizon hypothesis on the same inspected data. Freeze the new hypothesis before examining a fresh evaluation cohort and report that comparison regardless of outcome. The current latest-per-event cohort also contains only the three-hour snapshot, so a genuine horizon comparison requires an explicitly redesigned, grouped multi-horizon evaluation rather than merely relabeling these rows.

    Exercise 3: distinguishing the market's Brier from the training reference¶

    Explain, in one or two sentences, why market_brier and training_reference_brier answer different questions, and why a favorable gap between them is still not permission to trade on the difference.

    Solution sketch. market_brier asks how well a specific quoted number tracked the eventual realized label; training_reference_brier asks how well a single constant rate, learned only from earlier training data, would have done instead. A gap between them says the market's quote carried information beyond the base rate in this particular fixture, but it says nothing about executable prices, costs, fill probability, or whether that information is already reflected in what a real trader could actually pay to acquire the same position, so it cannot license a trading decision.

    Exercise 4: interpreting the NOAA result correctly¶

    A colleague reads the NOAA study's frozen Brier scores and concludes "seasonal patterns beat the market in prediction markets about climate contracts." Identify every part of that sentence that is not supported by the study, and restate a version that is.

    Solution sketch. The study contains no prediction-market contracts, prices, or trades of any kind, so "beat the market" is unsupported; it compares two forecasting models against each other, not against any executable quote. It is also not specific to "climate contracts," a category the study never constructs. A supported restatement: "a target-calendar-month seasonal rate produced a substantially lower Brier score than an expanding overall rate when forecasting month-over-month recorded CO2 increases across 132 evaluation months, using real but current-vintage NOAA observations and a hypothetical two-month reporting lag."
